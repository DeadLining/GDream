API Key 只能保存到 `settingsStore` 的凭证注册表，通过凭证引用读取；不得写入代码、默认配置、文档、日志、错误消息、命令行参数、项目导出或对话历史。本文档不保存任何真实密钥；历史上已经暴露的密钥必须废止并重新签发。

清除凭证时必须先判断是否被其他模型能力或生图槽位共享：独占凭证可以删除，共享凭证只能解除当前审核能力的绑定，不能破坏其他功能。

## 一、项目背景与问题定义

### 1.1 当前流程

```text
创意/文案
→ 剧本
→ 分镜
→ 视频提示词
→ 首尾帧或参考素材
→ 视频生成
→ 候选采用
```

现有流程已有基础功能，但缺少统一的镜头状态、跨镜头连续性、首尾帧审核、视频终审、有限重试、质量学习和交付门禁。

### 1.2 核心问题

1. 前一镜完成的动作会在后一镜被反向执行，道具在人物之间无原因来回变化；
2. 单镜头可能包含多个地点、时间跳跃和过多动作，模型无法稳定完成；
3. 首帧和尾帧没有分别对应时间轴的开始与结束状态；
4. 人物位置缺少稳定参照物、面朝方向、距离和运动路径；
5. 人物约束过死，导致表演僵硬、冻结、无口型；
6. `fl2va` 与 `ref2va` 使用了错误或混杂的素材引用语法；
7. 首尾帧未经审核就生成视频，错误被放大成付费废片；
8. 视频生成后无统一终审，不合格候选仍可能被采用；
9. 失败后整段重写或整轮重放，成本和结果不可控；
10. 缺少可追溯的审核记录、规则库和交付证据。

### 1.3 优化原则

1. 剧本决定剧情，视频提示词不得自行发展新剧情；
2. 连续性约束防止无因漂移，但不得冻结自然表演；
3. 空间关系使用参照物和相对关系，不使用不可执行的绝对坐标；
4. 首尾帧必须对应真实起止状态；
5. 审核失败只做最小修补，不重写整场；
6. 图片审核通过后才允许生成视频；
7. 视频终审通过后才允许正式采用和交付；
8. 已执行的付费任务不得自动整轮重放；
9. 自动重试必须有上限和人工接管出口；
10. 所有规则必须通用，不针对单一故事硬编码。

## 二、总体目标与目标流程

### 2.1 完整目标流程

```text
原始创意
→ 完整剧本
→ Scene 场景划分
→ Narrative Beat 叙事节拍
→ Atomic Shot 可生成镜头
→ entry_state / exit_state 连续性绑定
→ 视频提示词
→ 首帧提示词 / 尾帧提示词
→ 首尾帧生成
→ 首尾帧多模态审核
→ 最多三次最小修补与重绘
→ 视频生成
→ 视频多模态终审
→ 候选采用
→ 生产审计与交付清单
→ 高分提示词和问题规避规则沉淀
```

### 2.2 功能目标

1. 建立镜头级 `entry_state` 和 `exit_state`；
2. 建立相邻镜头默认状态继承；
3. 建立分镜级 Reviewer 和最小 Patch；
4. 建立适配不同 MiniMax-H3 任务类型的请求构造；
5. 建立首帧、尾帧独立提示词和资产映射；
6. 建立图片和视频两级多模态审核；
7. 建立首尾帧最多三次有限重绘；
8. 建立未审核、审核失败和人工复盘门禁；
9. 建立高分提示词库、问题规避规则库；
10. 建立 UI 状态、错误展示、生产审计和交付证据。

### 2.3 非目标

本轮不新建 Codex 生产后端，不把审核模型打包进应用，不让 Codex 在用户运行GDream时常驻，不执行无限重绘，不通过单一故事硬编码提升效果，也不在无用户授权时调用真实付费服务。

## 三、目标模块与数据模型

### 3.1 模块划分

1. 剧本与镜头规划模块；
2. 跨镜头连续性模块；
3. 视频、首帧和尾帧提示词模块；
4. 生成任务编排与恢复模块；
5. 多模态审核客户端；
6. 首尾帧有限重绘状态机；
7. 视频候选与终审模块；
8. 高分提示词和问题规则模块；
9. 生产审计与交付清单模块；
10. 设置、凭证和 UI 展示模块。

### 3.2 单镜头核心数据

每个可生成镜头至少保存：

```text
shot_id
scene_id
beat_id
script_revision
duration_seconds
video_prompt
submitted_video_prompt
prompt_fingerprint
task_type
bound_assets
entry_state
exit_state
transition_plan
first_frame_prompt
last_frame_prompt
first_frame_path
last_frame_path
frame_review
frame_attempt_count
video_candidates
selected_candidate
video_review
manual_review_required
last_production_packet
```

`shot_id` 是镜头在项目内的稳定身份，镜头编号和显示顺序可以调整，但更新、重写、选择、恢复和 React 列表键不得仅依赖可能重复或变化的 `shotNo`。每个候选必须保存自己的冻结生产包，不能依赖项目级“最近一次请求”反推历史输入。

### 3.4 候选生产包

每个视频候选的冻结生产包至少包含：稳定镜头 ID、剧本修订号、最终提交提示词全文、提示词指纹、任务类型、模型、Provider、条件顺序、条件 URI、首尾帧、参考资产、画幅、时长、生成参数、任务 ID、运行 ID、输入指纹、创建时间和恢复来源。

生产包一旦随候选写入，只能补充不改变语义的恢复元数据，不能被后续重写提示词、重新生成、项目切换或新的 `last_production_packet` 覆盖。

### 3.5 审核回执与配置绑定

首尾帧审核和视频终审回执必须绑定：审核类型、目标文件路径、目标内容指纹、输入提示词指纹、审核 Base URL 与模型组成的非密钥配置指纹、结构化评分、问题列表、建议补丁、审核时间和是否需要人工复盘。

文件被覆盖、提示词或输入资产改变、审核模型或地址改变时，历史回执可以保留用于审计，但不得继续作为当前通过依据。

### 3.3 连续性状态字段

`entry_state` 和 `exit_state` 至少描述：在场角色、角色身份、相对身高、相对位置、身体朝向、视线、姿态、动作阶段、情绪、持有道具、道具状态、场景拓扑、稳定参照物、时间、天气、光源、色调、摄影机位置、景别和画幅。

## 四、剧本、节拍与镜头规划规范

### 4.1 Scene 场景划分

地点明确切换、时间明显跳跃、环境条件无法连续解释，或进入梦境、回忆、幻觉和蒙太奇时，必须建立新的 Scene。

### 4.2 Narrative Beat 叙事节拍

每个 Beat 必须明确触发条件、核心动作、可见结果、情绪变化和对下一 Beat 的状态影响。

### 4.3 Atomic Shot 原子镜头

一个可生成镜头原则上只包含一个主要地点、一段连续时间、一个主要动作目标和一次核心状态变化，并能在计划时长内完整呈现。

镜头不是越细越好。连续动作、同一空间内的自然表演和同一情绪落点可以保留在一个镜头内；只有动作过载、场景切换、时间跳跃或状态矛盾时才拆镜。

### 4.4 跨镜头连续性

默认继承：

```text
Shot N.exit_state → Shot N+1.entry_state
```

继承人物、服装、伤势、道具归属、道具状态、相对位置、朝向、环境、光源和摄影机轴线。明确切场、跳时、蒙太奇、梦境，或剧本明确的瞬移、闪现、缩地、遁光和空间跃迁可以解除或改变继承，但必须写明原因和过程。

### 4.5 状态冲突检查

生成下一镜前必须检查：

1. 上一镜道具最后在谁手中；
2. 下一镜是否让道具无原因回到原处；
3. 人物是否无原因改变位置、朝向、服装或伤势；
4. 已完成动作是否重复执行；
5. 情绪结果是否被无原因重置；
6. 场景和时间是否冲突。

发现问题时优先修正下一镜的起始状态和动作衔接，不重写整场。

### 4.6 分镜级 Reviewer

Reviewer 检查单镜头是否跨时空、动作是否过载、对白与动作能否在计划时长内完成、首尾状态是否匹配、人物与道具是否连续、轴线是否合理、转场或超自然位移是否有依据。Reviewer 只能做最小 Patch，不改变剧情结局、人物关系、对白原文和核心动作。

## 五、视频提示词生成规范

### 5.1 提示词输入

视频提示词必须来自当前镜头脚本、`entry_state`、`exit_state`、上一镜 `exit_state`、绑定资产、任务类型、转场计划和问题规避规则。

### 5.2 提示词结构

每个镜头至少包含：场景设定、核心动作摘要、素材身份与用途、视觉媒介和角色身份、空间拓扑与开场状态、时间轴动作与表演、摄影机与构图、物理反馈、尾帧状态、声音与对白、连续性、受控转场和禁止项。

系统生成提示词、用户手工编辑提示词和 Provider 实际提交提示词必须区分保存。界面至少能查看当前正式提示词全文和本次真实提交提示词全文，并显示字符数、任务类型、生成时间和对应镜头。不得只显示被截断的卡片摘要后丢失原文。

### 5.3 时间轴动作与表演

1. 每段描述主要动作、动作目的、可见反馈和情绪方向；
2. 有对白时写清说话人、原文、开始和结束时间；
3. 说话人具有自然启唇、口型、下颌和脸颊运动；
4. 未说话人物不得形成语言，但允许呼吸、吞咽、眨眼和无声反应；
5. 表情写成自然变化方向，不逐帧锁死肌肉；
6. 允许服务核心动作或情绪落点的表情、手部、道具或接触特写；
7. 特写前后保持身份、面朝方向、左右轴线、身高比例和空间关系；
8. 最后一段必须有明确结束状态，不得只写“保持不动”；
9. 动作和对白总量必须能在镜头时长内完成。
10. MiniMax-H3 最终提交必须保留完整镜头提示词，禁止在提交前按固定字符数静默截断；如服务端存在明确长度上限，应在提交前显示可读错误并要求用户确认删减范围。

### 5.8 单镜提示词重写

“AI 重写本镜”必须使用当前最新的镜头提示词系统规则、当前项目上下文、稳定镜头 ID、该镜头脚本、连续性状态、任务类型和绑定资产，只更新用户点击的一个镜头。

调用开始时冻结项目 ID 与镜头 ID；模型返回后再次核对当前项目和目标镜头是否仍存在。用户已切换项目、删除镜头或目标身份不匹配时，必须丢弃迟到结果，不能写入另一个镜头。即使多个镜头显示相同 `shotNo`，也不能发生批量误覆盖。

重写前的提示词保留在编辑历史或可撤销状态中。单镜重写不得触发其他镜头重写、首尾帧生成、视频生成或任何付费工具。

### 5.9 提示词持久化与追溯

工坊镜头、分镜任务、首尾帧任务和 H3 视频任务的完整提示词必须持久化，不得套用通用任务卡片的 4000 字符摘要策略。若非工坊通用任务为了存储展示需要截断，必须显式保存 `promptTruncated=true` 和原始长度，且不得把摘要当成 Provider 实际提交文本。

恢复、候选详情、审核、交付清单和问题复盘读取的是候选或任务自己的完整提交快照，不读取当前编辑器里可能已变化的提示词代替历史事实。

### 5.4 空间关系

每个涉及移动的时间段应写明起始位置、稳定参照物、面朝方向、相对距离、移动路径、到达后的相对位置和环境反馈。

优先使用高台边缘、石阶、门框、桌边、车辆、落地道具或另一人物作为参照。人物尺度使用眼线高度差、肩线高度差、与门框或栏杆的相对高度、画面占比等表达。

不得只写“走到旁边”或“来到近处”，也不得笼统写“站位、姿态、视线、表情全程不变”。

### 5.5 自然走位与超自然位移

人物可以自然走动、转身、靠近、后退、弯腰、蹲下、踩踏、交接道具和改变重心。

剧情需要瞬移、闪现、缩地、遁光或空间跃迁时，可以直接写，但必须补全发动前位置、触发动作、残影或灵光特效、消失与现身衔接、落点、朝向、距离、风压、尘土、衣摆和光影反馈，以及与后续动作的连接。

### 5.6 对白和声音身份

1. 每句对白绑定唯一说话人；
2. 写清唯一允许的对白原文；
3. 不得改写、重复、增补或交给其他角色；
4. 群众环境声不得产生新的清晰台词；
5. 有声音资产时显式绑定；
6. 无声音资产时仍写明角色名称、性别、年龄和音色，降低角色串音和女角色说出男声的概率。

### 5.7 正确的连续性范围

锁定人物身份、基础脸型、年龄感、发型、无剧情依据的服装变化、道具身份、场景拓扑、光源逻辑、摄影机轴线、相对身高和已建立的左右关系。

允许位置、距离、姿态、重心、视线、表情、手势、衣摆、发丝、道具运动和有剧情依据的走位、瞬移、转身与镜头运动自然变化。

## 六、MiniMax-H3 任务类型适配

### 6.1 通用规则

文本提示词始终提交，但素材引用语法和 `conditions` 由任务类型决定。只传当前任务实际需要的字段，避免无关参数导致接口错误。

### 6.2 `fl2va`

1. `task` 显式为 `fl2va`；
2. `conditions` 必须恰好提交首帧和尾帧两个图片关键帧，不得缺少其中任意一张，也不得混入第三项条件；
3. 首帧：`role: keyframe`、`frame_index: 0`；
4. 尾帧：`role: keyframe`、`frame_index: -1`；
5. 提示词正文不得出现 `@图片一`、`@图片二` 或 `<Picture N>`；
6. 不额外提交该协议不要求的参考图条件。

```json
{
  "model": "MiniMaxAI/MiniMax-H3",
  "prompt": "完整视频提示词",
  "seconds": 5,
  "task": "fl2va",
  "conditions": [
    {"type":"image","uri":"file:///path/first.png","role":"keyframe","frame_index":0},
    {"type":"image","uri":"file:///path/last.png","role":"keyframe","frame_index":-1}
  ],
  "target": {"short_edge":768,"aspect_ratio":"auto","duration_seconds":5},
  "quality": "lossless",
  "num_outputs_per_prompt": 1,
  "num_inference_steps": 50,
  "flow_shift": 12,
  "audio_flow_shift": 3,
  "seed": 2101
}
```

### 6.3 `ref2va`

1. `task` 显式为 `ref2va`；
2. `conditions` 至少包含一个有效条目；
3. 图片、音频和视频按各自模态的一基顺序编号；
4. 提示词使用 `<Picture 1>`、`<Audio 1>`、`<Video 1>`；
5. 素材编号必须与 `conditions` 顺序一致；
6. 支持多张图片，不得在资产超过五张时静默不提交；
7. 只发送当前镜头需要的素材和参数。

`ref2va` 的“至少一项条件”属于不可绕过的协议门禁：提交前必须排除当前镜首帧和尾帧后重新统计实际参考图片、音频和视频；若数量为零，生成按钮应禁用并明确提示，不能通过“仍然继续”绕过。Provider 模态数量或总数超过上限时同样属于硬错误，必须在付费请求产生前阻断。

### 6.4 显式任务配置

界面必须显示当前任务类型，并根据任务类型展示所需素材。每次生成开始时必须把任务类型冻结到本次请求和生产输入包中，排队期间即使全局设置变化也不得改变已创建任务的条件集。切换任务类型不得删除资产，只改变本次请求映射。前置条件不满足时应在提交前给出明确提示，不能在用户尚未执行时显示“生成失败”。

任务输入必须互斥：`fl2va` 只把当前镜首帧和尾帧作为 keyframe 提交；`ref2va` 只提交当前镜参考资产以及有明确继承关系时的上一镜尾帧，不提交当前镜首尾帧；`t2va` 不提交任何图片、音频或视频条件。用户可以独立生成首尾帧用于预览或连续性准备，但非 `fl2va` 任务不得因为存在这些可选帧而自动混入请求、触发视频门禁或阻断交付。

### 6.5 服务地址和查询

1. Base URL 由用户配置，不硬编码 `7861`、`7863`、`18000` 或 `30010`；
2. 用户在浏览器打开的本地地址不等于GDream运行时必须调用的地址；
3. 提交成功后保存任务 ID并显示排队状态；
4. 查询间隔为 10 秒；
5. 不设置会错误终止慢任务的固定总超时；
6. 网络错误和远端任务失败分开显示；
7. 查询不得重复提交生成请求。

H3 前台轮询与应用重启后的恢复轮询都必须遵守上述规则。连续网络查询异常只能更新重试次数和可读状态，不能因为达到固定次数而把远端仍可能运行的任务判为失败；必须保留原任务 ID，每 10 秒继续查询，直到远端明确成功、明确失败或用户主动停止本地查询。

## 七、首尾帧提示词与生成规范

### 7.1 提示词来源

首帧与尾帧使用不同的信息边界：首帧只生成当前镜头 0.0 秒的可见状态；尾帧才依据完整时间轴推导结束结果。承接镜头的首帧必须以上一镜尾帧作为即时视觉主参考，逐项继承其可见资产、人物、位置、道具状态、光线、屏幕内容、空间轴线和摄影机状态，再叠加当前镜头的 0.0 秒开场状态。

### 7.2 首帧要求

首帧提示词包含资产用途、上一镜尾帧可见内容（如有）、继承的角色/场景/道具位置与状态、当前镜头 0.0 秒的面朝方向、视线、相对关系、画面占比、摄影机、场景和光源。不得包含完整动作时间轴、未来动作或本镜结束状态；未出现在上一镜尾帧中的资产不得仅因已上传而强行加入画面。

### 7.3 尾帧要求

尾帧提示词包含完整过程摘要、最后时间段的结束状态、人物和道具结果、相对位置、面朝方向、身高比例、摄影机最终位置和必要资产。不得无依据新增首帧中不存在且时间轴未说明进入画面的人物。

### 7.4 参考资产优先级

1. 核心角色资产；
2. 场景资产；
3. 核心道具资产；
4. 上一镜尾帧；
5. 当前镜头首帧，用于尾帧连续性；
6. 次要群像和风格资产。

如果生图模型存在参考图数量上限，按优先级选择，并在界面显示实际传入的图片，不得静默丢弃全部资产。

### 7.5 比例和查看

1. 首尾帧使用相同画幅和宽高比；
2. 不符合比例时裁切、扩图或重绘后再提交视频；
3. UI 显示尺寸和宽高比；
4. 首尾帧支持点击放大；
5. 用户可以展开查看实际提交的完整提示词和参考资产。

### 7.6 生成和重做

1. 首帧和尾帧使用不同提示词；
2. “生成首尾帧”只补齐缺失帧；
3. “重做首尾帧并生成”必须使旧审核失效并重新生成两张；
4. 仅尾帧有问题时只重做尾帧；
5. 帧路径、提示词、任务类型或资产签名变化时旧审核结果失效。

### 7.7 实际参考输入快照

首帧和尾帧必须分别保存本次真正提交给生图 Provider 的参考图片路径与用户可读标签，不能只保存原始候选资产列表。快照至少包含：

1. 首帧实际参考路径与标签；
2. 尾帧实际参考路径与标签；
3. 裁剪后的真实顺序和一基编号；
4. 当前镜首帧、上一镜尾帧、人物、场景、道具和其他参考的来源类型；
5. 与本次请求一致的参考输入签名。

Provider 参考图数量超限时，必须先按优先级裁剪，再基于裁剪结果同步生成请求数组、`@图片N` 或 `<Picture N>` 编号、边界帧签名、进度说明和审核输入。禁止只截断请求数组而保留指向旧顺序的提示词编号。

生成页必须分别展示“首帧实际输入”和“尾帧实际输入”，包括缩略图、编号和标签；缩略图支持点击放大。用户查看完整提示词时，必须能够同时确认实际提交素材、未提交素材和裁剪原因。

## 八、首尾帧多模态审核与有限重绘

### 8.1 审核输入

首帧、尾帧、完整视频提示词、首帧提示词、尾帧提示词、`entry_state`、`exit_state`、必要资产摘要、镜头时长、画幅和任务类型。

### 8.2 审核维度

1. 角色身份、相对身高和尺度；
2. 人物位置、朝向、视线和左右关系；
3. 场景拓扑、光源、天气和色调；
4. 道具归属、位置和状态；
5. 首帧是否符合开场；
6. 尾帧是否符合动作完成结果；
7. 摄影机变化是否有依据；
8. 是否无因新增或消失人物；
9. 是否有畸形、穿模、文字、水印或崩坏；
10. 首尾帧是否具备生成中间过程的可行性。

### 8.3 结构化结果

审核返回 `passed`、`score`、`summary` 和 `issues`。每个问题包含 `severity`、`category`、`target`、`description` 和 `suggested_patch`。存在 `error` 级问题时必须判定失败；解析失败、服务无响应或格式无效不得默认放行。

### 8.4 重绘状态机

1. 生成首尾帧；
2. 调用图片审核；
3. 通过后开放视频生成；
4. 失败后生成最小提示词补丁；
5. 仅尾帧问题只重绘尾帧；
6. 首帧或共同构图问题重绘两张；
7. 重绘后重新审核；
8. 最大尝试次数可配置为 1–3，默认 3；
9. 三次仍失败时标记人工复盘并阻断视频；
10. 人工修改脚本、提示词、资产或空间关系后可开始新周期。

最小补丁只修审核指出的尺度、朝向、道具、光源、构图等问题，不新增剧情，不替换对白。

### 8.5 审核配置绑定与状态展示

每份首尾帧审核和视频终审回执必须绑定审核 Base URL 与模型组合形成的非密钥配置指纹。指纹不得包含 API Key 原文。审核服务地址、模型、协议版本、目标文件、输入签名或关键审核规则变化后，历史回执保留用于追溯，但不得继续作为当前门禁的通过依据。

生成页和交付页必须区分三种状态：

1. 当前配置审核通过；
2. 当前配置审核未通过或尚未审核；
3. 存在历史审核结果，但因审核配置或生成输入变化已经失效，需要重新审核。

第三种状态不得显示为绿色“通过”，也不得允许采用或交付。重新审核只发起审核请求，不得因此自动重放付费生图或视频任务。

## 九、视频生成、候选与终审

### 9.1 生成前门禁

必须同时满足：视频提示词存在、任务类型明确、任务条件完整、素材路径有效、首尾帧审核通过且结果与当前文件和请求签名匹配、不处于人工复盘状态。

### 9.2 任务管理

提交后保存任务 ID。排队状态表示正在等待远端生成，不是前端卡死。每 10 秒查询同一任务，不重复提交。网络失败可继续查询；远端明确失败则停止并显示错误；用户取消默认只停止本地查询。

### 9.3 资产 URI

素材 URI 必须是视频服务实际可访问的位置。不得把本机 `/Users/<name>/...` 自动改成另一台服务器上不存在的路径。远端服务需要上传、共享目录或可访问 URL；同机服务可以使用真实本地路径。UI 不要求用户手工填写内部映射，但必须能查看最终提交 URI。

### 9.4 候选管理

每次成功生成保存独立候选。候选提供播放、下载、删除和采用；完整提示词放在详情中查看。未通过终审的候选可保留和下载用于分析，但不能正式采用。

删除必须经过候选生命周期门禁：不存在的候选不能删除，已经采用为正式视频的候选不能删除，只有当前仍存在且未采用的待选候选可以删除。若要删除正式候选，用户必须先明确改用其他候选或取消正式采用；不能出现“文件已经删掉但正式候选仍指向它”的状态。

采用候选后，视频文件下载能力必须保留；采用动作不应把播放、下载或生产包详情隐藏。删除失败只报告当前候选和文件操作错误，不得影响其他候选。

每个视频候选必须保存自己独立的生产输入包，至少包含模型、Provider 引擎、最终提交提示词、任务类型、按顺序排列的图片/音频/视频条件、首尾帧、上一镜尾帧、画幅、时长、生成参数、任务 ID、生产运行 ID、源剧本修订号、输入指纹和创建时间。`lastProductionPacket` 只能表示最近一次生成尝试，不得作为所有候选的共同世系来源。新的生成尝试失败、排队或覆盖最近尝试包时，已经采用的视频仍必须从自身候选生产包读取审计与交付证据，不能因此失效。

### 9.5 视频终审

终审输入包括完整视频、视频提示词、首尾帧、首尾状态、对白声音要求、候选 ID 和文件路径。

审核角色稳定性、相对尺度、位置朝向、动作顺序、道具状态、场景光影、摄影机与转场、超自然位移过程、对白说话人、口型、声画同步、穿模、闪烁、卡顿、文字和水印。

审核结果必须同时绑定具体候选路径和候选内容指纹。只有路径与候选指纹均匹配且审核通过后才允许采用；同一路径文件被覆盖、候选输入发生变化或审核属于其他候选时，旧结果必须失效。历史候选可以从审核历史中读取自己对应的终审结果。不通过时保留候选、阻断采用、给当前视频提示词追加最小补丁，但不得自动重新提交付费视频。

## 十、多模态审核服务配置

### 10.1 默认协议

1. 默认 Base URL：`http://127.0.0.1:30377`；
2. 默认模型：`qwen3.8-27b`；
3. OpenAI 兼容接口；
4. 审核请求：`/v1/chat/completions`；
5. 连接检查：`/v1/models`；
6. Base URL 已包含 `/v1` 时不得重复拼接；
7. API Key 由设置页凭证项提供。

审核客户端只依赖 OpenAI 兼容协议，不依赖 Codex。最小请求示意如下，示例中的占位符不得替换为真实密钥写入文档：

```http
POST /v1/chat/completions
Authorization: Bearer <API_KEY_FROM_CREDENTIAL_REGISTRY>
Content-Type: application/json
```

```json
{
  "model": "<configured-review-model>",
  "messages": [
    {
      "role": "system",
      "content": "<review-rubric-and-json-contract>"
    },
    {
      "role": "user",
      "content": "<text-and-multimodal-review-input>"
    }
  ],
  "temperature": 0.1
}
```

响应必须解析成GDream定义的结构化审核结果，而不是把任意自然语言直接视为通过。无法解析、缺字段、HTTP 错误或连接失败均返回“审核未完成”，不得默认通过。

### 10.2 设置项

设置页提供：启用开关、Base URL、模型名称、API Key 明文录入/临时显示与默认遮罩、已有凭证选择、最大首尾帧尝试次数、检查连接和清除凭证。连接测试只验证配置可用性，不输出请求头、Key 内容或完整服务错误正文。

设置保存后，业务模块只持有凭证引用；真正发送请求时再从 `settingsStore` 凭证注册表解析。设置导出、项目导出和错误反馈包均不得包含真实 Key。

“检查连接”只调用模型列表或健康接口，不触发图片、视频、配音或其他付费生成。

### 10.3 失败策略

连接超时、鉴权失败、模型不存在、协议错误、非 JSON 和审核不通过分别展示。图片审核不可用时阻断视频；视频终审不可用时阻断采用。关闭审核功能仅用于开发排查，生产审计和交付必须标记“未审核”，不能伪装为通过。

## 十一、质量学习与规则沉淀

### 11.1 高分提示词库

终审高分时保存提示词结构、时间轴密度、空间关系表达、摄影机和转场表达、任务类型、审核分数和镜头类型标签。只参考结构和细节密度，不复制其他镜头的剧情、人物、对白、场景或道具。

### 11.2 问题规避规则库

按缺陷沉淀人物朝向反转、尺度变化、道具归属错误、尾帧重复首帧、镜头位置不一致、对白串音、未说话角色口型、资产未提交、`fl2va` 出现素材编号、`ref2va` 编号顺序错误等规则。

高频规则按当前镜头相关性选择后自动注入，不能无限累加导致提示词失焦。

### 11.3 学习边界

不自动修改结局、不替换人物、不新增付费任务、不跨项目泄露素材、不把审核结果当绝对事实。用户可以查看、删除和重置学习记录。

### 11.4 项目质量统计

交付页应基于去重后的首尾帧审核和视频终审回执，展示审核总数、通过率、平均分、首尾帧与视频审核数量、需要人工复盘的镜头数量和最高频问题类型。统计只读取本项目已有回执，不调用模型、不改变提示词、不触发任何付费任务；同一回执同时存在于当前字段和历史记录时只能计算一次。

## 十二、界面与交互要求

### 12.1 镜头与提示词

1. 显示镜头数量和连续性状态；
2. 可查看 `entry_state`、`exit_state` 和上一镜继承；
3. 支持单个镜头“AI 重写本镜”；
4. 单镜重写使用与全量生成相同的最新逻辑，并真实调用文本模型；
5. 不要求确认导演预选方案；
6. 隐藏无实际用途且遮挡内容的图标；
7. 单镜重写的目标、列表键、批量选择和更新操作统一使用稳定镜头 ID，不只使用显示编号；
8. 显示加载、成功、失败和迟到结果已丢弃状态，项目切换或镜头删除后不得误写其他镜头；
9. 当前正式提示词和本次 Provider 实际提交提示词均可查看全文，并显示字符数与生成时间。

### 12.2 首尾帧

1. 提供“生成首尾帧”和“重做首尾帧并生成”；
2. 显示生成状态、尺寸、比例、实际提示词和实际参考资产；
3. 图片可点击放大；
4. 显示审核分数、尝试次数、摘要和问题列表；
5. 三次失败后显示人工复盘入口。

### 12.3 视频

1. 显示任务类型、任务 ID 和查询状态；
2. 显示排队、生成、成功、失败和取消；
3. 不显示错误的短超时倒计时；
4. 候选支持播放、下载、删除和采用；
5. 显示视频终审分数、摘要和问题；
6. 未通过终审时禁用采用；
7. 可查看完整视频提示词和最终请求配置；
8. 已采用候选继续提供播放、下载和生产包详情，但不能直接删除；
9. 只有存在且未采用的待选候选显示可执行删除，删除前二次确认；
10. 主要候选操作区不展示冗长提示词，完整文本放入详情弹窗。

### 12.4 错误状态

区分尚未执行、前置条件缺失、参数错误、网络失败、服务失败、任务失败、审核不通过、审核服务不可用、达到重试上限和用户取消。不能在用户没有执行时显示“生成失败”。

## 十三、成本、安全与恢复

### 13.1 付费任务控制

1. 单镜默认只生成首帧和尾帧各一张；
2. 审核失败只重绘必要帧；
3. 单审核周期最多三次；
4. 图片未通过不生成视频；
5. 视频失败或终审不通过不自动再提交；
6. 恢复任务先检查已有任务 ID 和候选文件；
7. 已执行的付费工具禁止整轮重放；
8. 批量生成前显示预计数量和影响范围。

### 13.2 幂等和恢复

每个任务保存唯一标识和请求签名。恢复时继续查询已有任务。结果落盘后先保存候选再终审。应用重启后可恢复排队任务和未完成审核。提示词、资产、任务类型或文件路径变化时使旧审核失效。

恢复视频任务时必须把本次任务对应的生产输入包写回恢复出的候选；打开旧项目时应兼容候选不含生产包的历史格式，并从可用的候选包或最近尝试包恢复生产运行映射。只有与候选输入指纹匹配的生产包才能作为该候选的正式证据。

### 13.3 日志和隐私

记录阶段、耗时、状态码和错误类型，但不记录 API Key。默认不把完整剧本和完整提示词写入系统日志。设置导出不含凭证，资产路径不发送给无关服务。

缺少审核、审核过期、候选未采用或人工复盘未完成时必须阻断交付。

## 十七、风险与回退

### 17.1 主要风险

审核服务不可用、生图参考图数量受限、本地路径对远端不可见、长提示词被截断、过度约束导致僵硬、约束不足导致漂移、自动重试导致成本增加、旧项目缺少字段、审核结果与新文件错配。

### 17.2 控制措施

审核失败关闭；参考资产按角色、场景、道具和连续性优先级选择；请求前展示实际条件；提示词结构化去重；只锁身份和空间逻辑；位置变化写参照物和路径；图片最多三次，视频不自动重试；新字段提供迁移默认值；审核结果绑定路径和签名。

### 17.3 回退原则

审核功能可关闭用于开发排查，但必须显示“未审核”。不删除已有候选和素材，不覆盖用户手工提示词，失败时保留原始提示词、补丁、审核结果和任务 ID。DSH 失败明确报错，不回退旧引擎或重放任务。

## 十九、最终结论

本轮优化不是增加一个 Codex 后端，也不是单纯把提示词写得更长，而是把GDream升级为一套具有明确剧情状态、空间关系、任务协议、质量审核、成本控制、恢复机制和交付证据的生产系统。

> 剧本负责把剧情组织为可生成的连续镜头；连续性层负责让人物、道具、空间和情绪在镜头内及镜头间合理传递；提示词负责准确呈现单镜头；首尾帧审核负责阻止错误进入视频生成；视频终审负责阻止不合格候选被采用；Codex 只负责把这些能力开发进GDream APP。

## 二十一、数据兼容与迁移要求

### 21.1 旧项目加载

1. 旧项目缺少新增字段时必须提供安全默认值，不得因 `undefined` 导致工作坊打不开；
2. 缺少连续性状态时允许显示“待重新规划”，但不得伪造已经审核通过；
3. 缺少候选生产包时按旧格式只读兼容，不得把当前全局配置错误绑定到历史候选；
4. 缺少审核签名时旧结果视为未绑定，不能直接作为新文件的通过证据；
5. 数据迁移不得删除用户已有提示词、素材、候选、任务 ID 或手工编辑内容。

### 21.2 签名失效规则

下列输入发生变化时，依赖它们的旧审核结果必须失效：

1. 视频提示词正文或镜头修订号变化；
2. 首帧、尾帧文件或其内容签名变化；
3. 生图模型、视频模型、H3 任务类型变化；
4. 资产图片集合、顺序或用途变化；
5. 审核模型、审核协议或关键审核规则变化；
6. 候选视频路径、文件签名或生产输入包变化。

审核结果失效只影响后续门禁，不自动删除旧文件和旧候选。

### 21.3 人工编辑优先级

用户手工编辑的提示词、镜头状态和候选选择必须保留。AI 重写只覆盖用户明确选择的镜头或字段；批量重新生成前必须明确展示影响范围，不能静默覆盖整套已编辑结果。

## 二十二、异常、恢复与幂等流程

### 22.1 提交失败

1. HTTP 4xx：展示服务返回的可读错误和本地校验原因，不进入排队状态；
2. HTTP 5xx：保留请求生产包和失败状态，允许用户手工重试，但不得自动重复付费提交；
3. 网络不可达：区分本机地址、远端地址和资产路径不可见问题；
4. `ref2va` 无有效条件：提交前阻断，明确说明当前镜首尾帧不属于参考条件；
5. Provider 模态数量超限：提交前阻断并展示实际数量、上限和被选素材。

### 22.2 查询失败

1. H3 任务提交成功后每 10 秒查询一次；
2. 不设置固定总生成超时；
3. 单次查询网络失败不创建新任务，只保留原任务 ID 继续恢复；
4. 应用重启后从持久化任务 ID 恢复查询；
5. 服务明确返回失败时停止查询并展示失败原因；
6. 用户手工取消查询不得被解释为取消远端付费任务，除非服务提供并成功执行取消接口。

### 22.3 候选失败隔离

每次视频生成形成独立候选和独立生产包。新候选失败、审核不通过或文件丢失，不得使已经存在的旧正式候选失效。只有用户明确采用新的合格候选后，正式候选指针才允许变化。

## 二十三、完整界面流程

### 23.1 设置页

用户可以配置 MiniMax-H3 Base URL、模型、任务类型默认值、多模态审核 Base URL、审核模型、最大尝试次数和审核 API Key。API Key 输入项必须明确可见并可执行保存、替换、清除和连接检查，但真实值不得在保存后回显到日志或项目文件。

### 23.2 剧本与分镜

用户输入初步 Idea 后可调用 Story Director 规则和已配置文本模型生成文案；生成结果可以导入工作坊。分镜阶段展示 Scene、Narrative Beat、Atomic Shot、连续性模式、入口状态、出口状态和 Reviewer 结果。去除不必要的导演预选确认，避免阻塞正常流程。

### 23.3 提示词

每个镜头显示当前正式视频提示词，可点击查看全文，并支持只对本镜执行“AI 重写本镜”。单镜重写使用当前最新系统规则，不重新生成其他镜头，不静默覆盖用户手工修改的其他内容。

### 23.4 首尾帧

没有首尾帧时提供“生成首尾帧”；已有首尾帧时提供“重做首尾帧并生成”。首帧和尾帧缩略图可点击放大，界面可查看实际生图提示词、使用的资产和审核状态。首帧、尾帧分别展示本次真实提交的参考图缩略图、顺序编号和用途标签，不能用项目全部资产冒充实际输入。首尾帧保持相同画幅和分辨率策略。

### 23.5 视频生成

任务类型必须显式配置。`fl2va` 展示首帧和尾帧条件，`ref2va` 展示实际参考图片、音频、视频和继承尾帧，`t2va` 不展示虚假的素材条件。点击提交前展示真实文本提示词、任务类型、条件数量、目标比例和时长。

### 23.6 候选和交付

每个候选支持播放、下载、删除、查看审核结果和查看生产输入包。候选采用后仍可下载。交付阶段展示正式候选、审核状态、任务 ID、运行 ID、剧本修订号、提示词指纹、条件指纹和文件可用性。

## 二十五、当前实现证据与已知限制

### 25.1 截至 2026-08-30 的实现证据

当前开发分支为 `codex/atomic-shot-continuity`。已完成的代码能力包括原子镜头规划、跨镜头状态、分镜 Reviewer、H3 三类任务适配、10 秒查询、首尾帧生成和审核、有限重绘、视频候选终审、候选级生产包、生产审计、交付清单、单镜 AI 重写、图片放大、提示词全文查看、候选播放下载删除采用、审核凭证保存与清除，以及质量学习记录的查看、完整提示词展开、单条删除和全部重置。

单镜 AI 重写现按稳定镜头 ID 更新：调用开始时冻结项目 ID 与镜头 ID，返回时再次确认项目和镜头仍有效；项目切换、镜头删除或目标不匹配时丢弃迟到结果。镜头列表键和批量选择同样使用稳定 ID，重复显示编号不会造成多个镜头被同时覆盖。

候选删除现经过独立生命周期门禁：正式采用候选和不存在候选均不能删除，只有存在且未采用的待选候选可以进入确认和文件删除流程。采用候选的播放、下载和生产包追溯不受影响。

Idea 文案入口由GDream文案工作室自身的文本模型 Agent 执行，Codex 不参与运行时生成。原先依赖视图切换后固定等待 450ms 再广播窗口事件，存在文案面板尚未挂载时提示词丢失的竞态；现改为本地持久提示词桥，先点击 Idea、后挂载文案视图时仍会按顺序消费请求。

候选采用已统一以候选自身冻结的生产包为权威来源；后续失败尝试不会使旧正式候选的生产世系失效。旧项目中的不完整生产包会安全归一化，缺失字段不会导致项目加载崩溃，也不会被补造成有效指纹。多模态审核回执现绑定审核服务地址与模型的非密钥指纹，切换 Base URL 或模型后，旧审核在生成、候选采用、生产审计和交付清单中自动失效。

恢复中的工坊视频任务现另外持久化任务自身的 `workshopProductionPacket`。应用重启回填候选时优先使用任务自身冻结包，并强制核对 `inputFingerprint`；只有旧任务缺少独立包时，才允许回退到同指纹的镜头最近包。后续重新生成覆盖 `lastProductionPacket` 不会再让旧任务借用错误提示词、素材或任务参数，也不会破坏原候选世系。

首尾帧生图已建立 Provider 参考图上限和通用优先级策略。GPT-Image-2、Seedream 5 Pro 与 Midjourney 路径最多提交 10 张参考图；尾帧首先保留当前镜首帧，其次保留上一镜尾帧、人物资产、主场景和关键道具，再考虑场景补充角度、额外参考和色卡。发生裁剪时，实际请求、提示词图片编号、边界帧签名和用户可见提交说明同步更新，不再出现数组被截断但 `@图片N` 仍指向旧素材的问题。

每个镜头现分别保存首帧和尾帧真正提交给生图模型的参考图片路径与标签快照。生成页展示“首帧实际输入”和“尾帧实际输入”的缩略图、编号及用途标签，图片可点击放大；用户可以据此核对 Provider 实际接收的素材，而不是只能看到项目资产全集。输入失效、重新生成或请求裁剪时，对应快照和签名同步更新或清除。

首尾帧和视频审核回执现绑定审核 Base URL 与模型的非密钥配置指纹。生成页审核卡明确显示“当前通过”“当前未通过或未审核”“历史结果已失效，需重审”三种状态；切换审核服务或模型后，历史结果不会被误显示为当前通过，也不能继续通过候选采用、生产审计或交付门禁。

本轮进一步收紧 H3 付费提交协议：`fl2va` 必须恰好提交按顺序排列的首帧 `frame_index=0` 与尾帧 `frame_index=-1`，`ref2va` 只能提交 `role=reference` 的实际参考素材，`t2va` 必须保持空条件。自定义 SGLang H3 不再把完整视频提示词静默截断为 12000 字符，尾部对白、连续性、尾帧验收和禁止项能够完整进入请求。

H3 前台和后台恢复均保持 10 秒查询间隔且无固定总时长；后台连续查询异常也不再因达到 30 次而把任务判为失败，而是保留原任务 ID 持续恢复。`fl2va` 视频提交增加首尾帧审核硬门禁：审核关闭、未审核、审核失败、签名过期、审核服务或模型变化以及进入人工复盘状态时，均在付费视频请求前阻断。

隐私日志已继续收紧：画布生图不再输出完整提示词，配音参考文件读取失败不再输出本地资产路径，只保留必要的长度、模式和错误类型信息。

设置备份已移除“含密钥导出”能力。所有设置导出统一排除凭证注册表、凭证引用、旧平铺 API Key、COS Secret、Provider Key 表、带内联 Key 的生图槽位和 token 字段；旧备份仍可导入。审核凭证清除策略已提取为纯函数：独占凭证才从注册表删除，被其他能力或生图槽位共享时只解绑审核能力。

项目 ZIP 导出层现对工坊和画布 JSON 递归移除 API Key、Secret、Authorization、token、凭证注册表与引用字段；敏感字段即使伪装成本地文件路径，也不会进入资产扫描和附加打包。无法解析的项目 JSON 将阻止导出，而不是把可能含明文凭证的原始内容直接写入 ZIP。

旧项目加载的基础迁移已提取为纯函数，直接覆盖缺失默认数组、旧资产只有 `assetImagePath`、镜头缺少或重复 ID、旧候选与提示词保留、以及不完整生产包不得伪造有效指纹。迁移后仍继续执行现有色卡、验收绑定、运行映射和文件校验流程。

| 历史审核 | 保留用于追溯但不能继续通过当前门禁的旧回执 |
| `fl2va` | 以前后关键帧和文本生成视频的 H3 任务 |
| `ref2va` | 以图片、音频或视频参考条件和文本生成视频的 H3 任务 |
| `t2va` | 只用文本条件生成视频的 H3 任务 |
| 最小 Patch | 只修复审核指出问题、不改变剧情和核心动作的局部修正 |
| 人工复盘 | 自动有限重试结束后由用户决定如何修改和是否继续付费生成 |
